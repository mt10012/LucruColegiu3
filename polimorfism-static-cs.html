Polimorfism Static
în C#

O explorare aprofundată a polimorfismului static — cum funcționează, de ce există și cum îl aplici în practică, explicat din mai multe unghiuri.

~30 min lectură 4 secțiuni Exemple cod C#

Ce este polimorfismul static?

Polimorfismul este unul dintre pilonii fundamentali ai programării orientate obiect. Există două forme principale — statică și dinamică. Să înțelegem mai întâi ce înseamnă forma statică și de unde vine necesitatea ei.

Definiție simplă
Rezolvat la compilare

Polimorfismul static înseamnă că decizia despre care versiune a unei metode se apelează se ia la momentul compilării, nu la rulare. Compilatorul știe dinainte ce cod va executa.

Denumire tehnică
Early Binding

Se mai numește legare timpurie (early binding). Spre deosebire de polimorfismul dinamic (late binding), nu există niciun cost de căutare la runtime — totul este rezolvat de compilator.

1 Analogia cu aparatul de cafea

☕
Butoane diferite, aceeași acțiune conceptuală

Imaginează-ți un aparat de cafea cu trei butoane: espresso, cappuccino, americano. Toate "fac cafea" — aceeași idee generală — dar fiecare buton declanșează un proces diferit. Când apeși butonul, aparatul știe dinainte (la "compilare") ce va face. Nu decide în momentul apăsării care metodă să ruleze; este prestabilit prin design. Acesta este polimorfismul static.

🔧
Trusa de scule cu capete interschimbabile

Un mecanic are o singură cheie, dar capete diferite — pentru șuruburi de 10mm, 12mm, 14mm. Funcția este aceeași conceptual (strânge șurub), dar parametrul (dimensiunea) determină ce cap folosești. Compilatorul vede ce dimensiune ai și "alege" capul potrivit înainte să înceapă treaba. Nu există nicio decizie la momentul execuției.

🗺️
GPS cu itinerare prestabilite

Un sistem GPS care cunoaște din start trei rute posibile între două orașe — pe autostradă, pe drum național, pe drumuri lăturalnice. Înainte să pornești la drum, GPS-ul îți afișează ruta completă; nu recalculează în mers. Polimorfismul static funcționează la fel: compilatorul trasează "ruta" (apelul de metodă corect) înainte de execuție, pe baza informațiilor disponibile la compilare.

2 Formele polimorfismului static în C#

1
Supraîncărcarea metodelor (Method Overloading)

Mai multe metode cu același nume, dar cu semnături diferite (parametri diferiți). Compilatorul alege metoda potrivită în funcție de tipul și numărul argumentelor. Este cea mai frecvent întâlnită formă în codul de zi cu zi.

2
Supraîncărcarea operatorilor (Operator Overloading)

Redefinirea comportamentului operatorilor (+, -, *, etc.) pentru tipuri de date personalizate. Compilatorul traduce expresia a + b în apelul metodei op_Addition(a, b). Util în special pentru tipuri matematice sau structuri de date custom.

3
Generice / Parametri de tip (Generics)

Clase și metode parametrizate cu tipuri. List<int> vs List<string> — compilatorul generează cod specific pentru fiecare tip, evitând boxing și asigurând siguranță la compilare.

3 Cum vede compilatorul codul

Să urmărim pas cu pas ce se întâmplă atunci când compilatorul C# întâlnește un apel de metodă supraîncărcată.

ResolutionDemo.csC#
public class Printer
{
    public void Print(int x)    { Console.WriteLine("int: " + x); }
    public void Print(double x) { Console.WriteLine("double: " + x); }
    public void Print(string x) { Console.WriteLine("string: " + x); }
}

Printer p = new Printer();

// Pasul 1 — compilatorul vede literalul 42 → tip int → alege Print(int)
p.Print(42);           // → "int: 42"

// Pasul 2 — 3.14 este double literal → alege Print(double)
p.Print(3.14);         // → "double: 3.14"

// Pasul 3 — "salut" este string literal → alege Print(string)
p.Print("salut");      // → "string: salut"

// Pasul 4 — variabilă de tip int → rezolvat la compilare, nu la runtime
int numar = 100;
p.Print(numar);        // → "int: 100" — ales la compilare!
🔍 CE SE ÎNTÂMPLĂ ÎN SPATE

Compilatorul C# parcurge un algoritm de rezoluție a supraîncărcării (overload resolution) în mai mulți pași: mai întâi identifică toate metodele cu același nume, apoi elimină pe cele cu număr incompatibil de parametri, apoi aplică conversiile implicite posibile, și în final alege cea mai specifică potrivire. Dacă nu există o potrivire unică, rezultă o eroare de compilare — niciodată o surpriză la runtime.

4 Polimorfism static vs polimorfism dinamic — prima privire

Chiar de la început, merită să înțelegi cum se deosebesc cele două forme. Vom detalia în secțiunea 4, dar iată esența:

PrimaComparatie.csC#
// ── STATIC: compilatorul alege la build time ──────────────
public class Salut
{
    public void Afiseaza(string nume)
        => Console.WriteLine($"Bună, {nume}!");

    public void Afiseaza(string nume, string titlu)
        => Console.WriteLine($"Bună, {titlu} {nume}!");
}
// La compilare: Afiseaza("Ana") → prima variantă, întotdeauna.


// ── DINAMIC: runtime-ul alege la execuție ─────────────────
public abstract class Forma
{
    public abstract double Arie();
}
public class Cerc : Forma
{
    public double Raza;
    public override double Arie() => Math.PI * Raza * Raza;
}
// La runtime: forma.Arie() poate fi Cerc.Arie(), Patrat.Arie() etc.
// Depinde de tipul real al obiectului — necunoscut la compilare.
💡 DE REȚINUT

Polimorfismul static nu înlocuiește polimorfismul dinamic — le servesc scopuri diferite. Cel static oferă performanță maximă și siguranță la compilare. Cel dinamic oferă flexibilitate la runtime. Un programator bun știe când să folosească fiecare.

O regulă practică: dacă știi exact cu ce tipuri lucrezi și logica nu se schimbă în funcție de tipul obiectului la runtime → polimorfism static. Dacă ai o ierarhie de obiecte cu comportament diferit care se poate extinde în viitor → polimorfism dinamic.

5 Avantajele polimorfismului static

⚡
Performanță zero-overhead

Nu există nicio structură suplimentară de tabele virtuale (vtable), nicio căutare la runtime, niciun nivel de indirectare. Apelul de metodă este compilat direct în instrucțiunea de salt corectă. În aplicații cu bucle strânse sau sisteme critice la performanță, această diferență contează.

🛡️
Siguranță la compilare

Orice eroare de tip (de exemplu, pasarea unui bool acolo unde se așteaptă un int fără conversie implicită) este detectată înainte ca programul să ruleze. Nu ajungi la InvalidCastException sau comportament ciudat la runtime.

📖
Lizibilitate și intenție clară

A putea scrie calc.Aduna(3, 4) și calc.Aduna(3.14, 2.71) cu același nume de metodă face codul mai natural de citit. Alternativa — AdunaIntregi, AdunaDouble, AdunaTriple — poluează namespace-ul și crește sarcina cognitivă.

Supraîncărcarea metodelor

Method overloading este cea mai comună formă de polimorfism static. Permite definirea mai multor versiuni ale aceleiași metode, diferențiate prin semnătura lor. Este o funcționalitate pe care o vei folosi zilnic în C#.

1 Exemplu de bază

Calculator.csC#
public class Calculator
{
    // Versiunea pentru int
    public int Aduna(int a, int b)
    {
        return a + b;
    }

    // Versiunea pentru double
    public double Aduna(double a, double b)
    {
        return a + b;
    }

    // Versiunea cu trei parametri
    public int Aduna(int a, int b, int c)
    {
        return a + b + c;
    }

    // Versiunea pentru string (concatenare)
    public string Aduna(string a, string b)
    {
        return a + b;
    }
}
🔍 CE FACE COMPILATORUL

Când scrii calc.Aduna(3, 4), compilatorul vede că ambele argumente sunt int și alege prima supraîncărcare. Când scrii calc.Aduna(3.14, 2.71), alege a doua. Această decizie este finală la compilare — la runtime nu există nicio verificare sau decizie suplimentară.

2 Supraîncărcarea cu parametri opționali și params

C# oferă și alte mecanisme legate de supraîncărcare: parametrii opționali (cu valori implicite) și cuvântul cheie params, care permit flexibilitate fără a defini zeci de supraîncărcări manuale.

ParametriOptionali.csC#
public class Mesagerie
{
    // Parametri opționali — valori implicite
    public void TrimiteEmail(
        string destinatar,
        string subiect = "Fără subiect",
        bool urgent = false)
    {
        string prefix = urgent ? "[URGENT] " : "";
        Console.WriteLine($"Către: {destinatar} | {prefix}{subiect}");
    }

    // params — număr variabil de argumente
    public int Suma(params int[] numere)
    {
        int total = 0;
        foreach (int n in numere) total += n;
        return total;
    }
}

// Utilizare
Mesagerie m = new Mesagerie();
m.TrimiteEmail("ana@test.ro");                          // subiect implicit
m.TrimiteEmail("ion@test.ro", "Întâlnire mâine");        // fără urgent
m.TrimiteEmail("sef@test.ro", "Raport", true);           // toți parametrii

int s1 = m.Suma(1, 2, 3);              // → 6
int s2 = m.Suma(10, 20, 30, 40, 50);   // → 150
⚠️ ATENȚIE LA AMBIGUITATE

Dacă ai atât o supraîncărcare explicită cât și parametri opționali care ar putea să se suprapună, compilatorul C# va prefera întotdeauna metoda cu corespondență exactă față de cea cu parametri opționali. De exemplu, dacă există Suma(int a, int b) și Suma(params int[] n), apelul Suma(1, 2) va folosi prima variantă. Reține această regulă pentru a evita comportamente neașteptate.

3 Supraîncărcarea operatorilor

Punct2D.csC#
public class Punct2D
{
    public double X { get; set; }
    public double Y { get; set; }

    public Punct2D(double x, double y)
    {
        X = x;
        Y = y;
    }

    // Supraîncărcăm operatorul +
    public static Punct2D operator +(Punct2D a, Punct2D b)
    {
        return new Punct2D(a.X + b.X, a.Y + b.Y);
    }

    // Supraîncărcăm operatorul -
    public static Punct2D operator -(Punct2D a, Punct2D b)
    {
        return new Punct2D(a.X - b.X, a.Y - b.Y);
    }

    // Supraîncărcăm operatorul * cu un scalar
    public static Punct2D operator *(Punct2D p, double factor)
    {
        return new Punct2D(p.X * factor, p.Y * factor);
    }

    // Supraîncărcăm operatorul ==
    public static bool operator ==(Punct2D a, Punct2D b)
    {
        return a.X == b.X && a.Y == b.Y;
    }

    public static bool operator !=(Punct2D a, Punct2D b)
    {
        return !(a == b);
    }

    // Distanța față de origine
    public double Lungime()
        => Math.Sqrt(X * X + Y * Y);

    public override string ToString()
    {
        return $"({X}, {Y})";
    }
}

// Utilizare
Punct2D p1 = new Punct2D(2, 3);
Punct2D p2 = new Punct2D(4, 1);
Punct2D p3 = p1 + p2;          // → (6, 4)
Punct2D p4 = p1 - p2;          // → (-2, 2)
Punct2D p5 = p1 * 3.0;         // → (6, 9)
bool egal = (p1 == p2);        // → false
Console.WriteLine(p3.Lungime()); // distanța față de (0,0)
✅ DE CE ESTE UTIL

Fără supraîncărcarea operatorului, ar trebui să scrii Punct2D p3 = Punct2D.Aduna(p1, p2). Cu supraîncărcare, codul devine natural și lizibil: p3 = p1 + p2. Compilatorul transformă automat operatorul + în apelul metodei statice corespunzătoare.

Acest pattern este extrem de util în domeniile în care matematica joacă un rol central: grafică 2D/3D, motoare de fizică, calcule financiare, procesare de semnale. Librariile populare precum Unity (Vector2, Vector3) sau System.Numerics folosesc supraîncărcarea operatorilor pe scară largă exact din acest motiv.

4 Exemplu aplicat — clasa Fracție

Un exemplu mai complet care combină supraîncărcarea metodelor și a operatorilor: o clasă pentru fracții matematice.

Fractie.csC#
public class Fractie
{
    public int Numarator   { get; }
    public int Numitor     { get; }

    public Fractie(int numarator, int numitor)
    {
        if (numitor == 0) throw new ArgumentException("Numitor 0!");
        int d = Cmmdc(Math.Abs(numarator), Math.Abs(numitor));
        Numarator = numarator / d;
        Numitor   = numitor / d;
    }

    // Supraîncărcare + pentru fracții
    public static Fractie operator +(Fractie a, Fractie b)
        => new Fractie(
            a.Numarator * b.Numitor + b.Numarator * a.Numitor,
            a.Numitor * b.Numitor);

    // Supraîncărcare * pentru fracții
    public static Fractie operator *(Fractie a, Fractie b)
        => new Fractie(a.Numarator * b.Numarator, a.Numitor * b.Numitor);

    // Conversie implicită la double
    public static implicit operator double(Fractie f)
        => (double)f.Numarator / f.Numitor;

    private static int Cmmdc(int a, int b)
        => b == 0 ? a : Cmmdc(b, a % b);

    public override string ToString()
        => $"{Numarator}/{Numitor}";
}

// Utilizare
Fractie f1 = new Fractie(1, 2);   // 1/2
Fractie f2 = new Fractie(1, 3);   // 1/3
Fractie suma = f1 + f2;            // → 5/6
Fractie prod = f1 * f2;            // → 1/6
double val = f1;                   // → 0.5 (conversie implicită)
Console.WriteLine(suma);            // → "5/6"

5 Reguli importante

⚠️ CE NU SE POATE — tipul de return

Două metode NU pot forma supraîncărcare validă dacă diferă doar prin tipul de return. De exemplu, int Calcul(int x) și double Calcul(int x) vor provoca eroare de compilare — compilatorul nu poate distinge între ele după semnătură.

📋 REGULI COMPLETE DE SUPRAÎNCĂRCARE

Se poate supraîncărca diferind prin: numărul de parametri, tipul parametrilor, ordinea parametrilor (dacă tipurile sunt diferite).

Nu se poate supraîncărca diferind doar prin: tipul de return, numele parametrilor (ex: int x vs int y), cuvintele cheie ref/out între ele (deși ref/out vs nimic creează o semnătură diferită).

6 Supraîncărcarea în constructori

Supraîncărcarea nu se aplică doar metodelor obișnuite — constructorii pot fi și ei supraîncărcați, ceea ce este o practică extrem de frecventă.

Persoana.csC#
public class Persoana
{
    public string Nume    { get; }
    public int    Varsta  { get; }
    public string Email   { get; }

    // Constructor minimal
    public Persoana(string nume)
        : this(nume, 0, "") { }

    // Constructor cu vârstă
    public Persoana(string nume, int varsta)
        : this(nume, varsta, "") { }

    // Constructor complet — delegat de ceilalți prin : this(...)
    public Persoana(string nume, int varsta, string email)
    {
        Nume   = nume;
        Varsta = varsta;
        Email  = email;
    }

    public override string ToString()
        => $"{Nume}, {Varsta} ani, {Email}";
}

// Utilizare
Persoana p1 = new Persoana("Ana");
Persoana p2 = new Persoana("Ion", 25);
Persoana p3 = new Persoana("Maria", 30, "maria@ex.ro");
✅ PATTERN: CONSTRUCTOR CHAINING

Folosind : this(...), constructorii mai simpli îl delegă pe cel mai complet. Astfel logica de inițializare există într-un singur loc, nu duplicată în fiecare constructor. Aceasta este o bună practică recomandată de standardele de cod C# pentru a evita erori de sincronizare când constructorul principal se schimbă.

Generice — polimorfism static avansat

Genericele (Generics) în C# reprezintă o formă sofisticată de polimorfism static. Ele permit scrierea de cod reutilizabil care funcționează cu orice tip, cu toate verificările făcute la compilare. Fără generice, o mare parte din biblioteca standard C# pur și simplu nu ar putea exista în forma sa actuală.

1 Problema fără generice

FaraGenerice.cs — ProblemaC#
// Varianta proastă — fără generice
public class CutieInt
{
    private int _valoare;
    public void Pune(int val) { _valoare = val; }
    public int Ia() { return _valoare; }
}

public class CutieString
{
    private string _valoare;
    public void Pune(string val) { _valoare = val; }
    public string Ia() { return _valoare; }
}
// Ar trebui să repetăm pentru fiecare tip... nepractic!


// Varianta cu object — mai flexibilă, dar cu probleme
public class CutieObject
{
    private object _valoare;
    public void Pune(object val) { _valoare = val; }
    public object Ia() { return _valoare; }
}

// Problemele apar la utilizare:
CutieObject cutie = new CutieObject();
cutie.Pune(42);
int val = (int)cutie.Ia(); // cast manual — risc de InvalidCastException!
cutie.Pune("eroare");
int gresit = (int)cutie.Ia(); // CRASH la runtime — compilatorul n-a prins!
⚠️ DE CE object NU ESTE SOLUȚIA

Folosind object ca tip universal se pierde siguranța la compilare și apare boxing — procesul costisitor prin care valorile de tip valoare (int, double, struct) sunt împachetate în obiecte heap. Înainte de C# 2.0 și introducerea genericelor (2005), ArrayList folosea object, iar erorile de casting la runtime erau o problemă reală în aplicații mari.

2 Soluția cu generice

Cutie.cs — Soluția cu genericeC#
// O singură clasă generică
public class Cutie<T>
{
    private T _valoare;

    public void Pune(T val)
    {
        _valoare = val;
    }

    public T Ia()
    {
        return _valoare;
    }
}

// Utilizare — compilatorul generează cod specific
Cutie<int> cutieInt = new Cutie<int>();
cutieInt.Pune(42);
int val = cutieInt.Ia(); // Tipul este verificat la compilare!

Cutie<string> cutieStr = new Cutie<string>();
cutieStr.Pune("Salut");
string text = cutieStr.Ia(); // Funcționează perfect

// Compilatorul NU permite tipuri greșite:
// cutieInt.Pune("text"); ← EROARE DE COMPILARE — în siguranță!

3 Metode generice și constrângeri

Utilitare.csC#
public class Utilitare
{
    // Metodă generică simplă
    public static void Afiseaza<T>(T element)
    {
        Console.WriteLine($"Valoare: {element}");
    }

    // Cu constrângere — T trebuie să implementeze IComparable
    public static T Maxim<T>(T a, T b) where T : IComparable<T>
    {
        return a.CompareTo(b) > 0 ? a : b;
    }

    // Cu constrângere — T trebuie să fie clasă cu constructor fără parametri
    public static T CreeazaNou<T>() where T : class, new()
    {
        return new T();
    }
}

// Utilizare
Utilitare.Afiseaza(42);          // T = int
Utilitare.Afiseaza("Matei");    // T = string

int mare = Utilitare.Maxim(10, 25);        // → 25
string ultim = Utilitare.Maxim("ana", "zoe"); // → "zoe"
💡 DE CE ESTE POLIMORFISM STATIC

Când compilatorul vede Maxim<int>(10, 25), el generează o versiune specifică a metodei pentru tipul int. Când vede Maxim<string>, generează alta. Fiecare versiune este specifică tipului și complet verificată — niciun risc de eroare la runtime din cauza tipurilor incompatibile.

4 Tipuri de constrângeri (where)

Constrângerile generice sunt unul dintre cele mai puternice instrumente din C#. Ele îți permit să restrângi ce tipuri pot fi folosite cu un parametru generic, deblockând în același timp metode și proprietăți specifice acelui tip.

Constrangeri.cs — Tipuri de whereC#
// where T : struct          → T trebuie să fie tip valoare (int, double, struct)
public static T ValoareDefault<T>() where T : struct
    => default(T); // pentru int → 0, pentru bool → false

// where T : class           → T trebuie să fie tip referință
public static bool EsteNull<T>(T obj) where T : class
    => obj == null;

// where T : InterfataMea     → T trebuie să implementeze interfața
public static void Proceseaza<T>(T item) where T : IDisposable
{
    using (T resource = item)
    {
        // item.Dispose() disponibil datorită constrângerii
    }
}

// where T : ClassaBaza       → T trebuie să fie acea clasă sau subclasă
public static void Salveaza<T>(T entitate) where T : EntitateDB
{
    Console.WriteLine($"Salvez {entitate.TabelNume}"); // proprietate din clasa bază
}

// Constrângeri multiple — combinate cu virgulă
public static T ClonaEgala<T>(T sursa)
    where T : class, ICloneable, new()
{
    return (T)sursa.Clone();
}

5 Colecții generice din biblioteca standard

Genericele sunt omniprezente în biblioteca standard C#. Iată câteva dintre cele mai utilizate colecții generice și cum se compară cu variantele ne-generice mai vechi:

GENERICE (recomandat)
  • List<T> — listă dinamică tipizată
  • Dictionary<TKey, TValue> — map tip-safe
  • Queue<T> — coadă tipizată
  • Stack<T> — stivă tipizată
  • HashSet<T> — mulțime tipizată
  • Fără boxing, fără cast, erori la compilare
NE-GENERICE (evitate)
  • ArrayList — stochează object
  • Hashtable — chei și valori object
  • Queue — elemete de tip object
  • Stack — elemente de tip object
  • Boxing pentru tipuri valoare
  • Cast manual, riscuri la runtime
ColectiiGenerice.csC#
// List<T> — cel mai folosit tip generic din C#
List<string> studenti = new List<string>();
studenti.Add("Ana");
studenti.Add("Ion");
studenti.Add("Maria");

6 Interfețe generice comune

Genericele strălucesc cu adevărat atunci când sunt combinate cu interfețe generice. Iată câteva interfețe generice din .NET pe care le vei întâlni frecvent:

InterfeteGenerice.csC#
// IEnumerable<T> — orice colecție iterabilă
public void AfiseazaTot<T>(IEnumerable<T> colectie)
{
    foreach (T item in colectie)
        Console.WriteLine(item);
}
// Funcționează cu List<T>, T[], Queue<T>, orice altceva!


// IComparable<T> — pentru comparare și sortare
public class Student : IComparable<Student>
{
    public string Nume  { get; set; }
    public double Medie { get; set; }

    public int CompareTo(Student other)
        => this.Medie.CompareTo(other.Medie);
}

// Acum putem sorta o List<Student> direct
List<Student> clasa = new List<Student> { /* ... */ };
clasa.Sort(); // folosește CompareTo — totul type-safe!

public class Produs : IEquatable<Produs>
{
    public int    Id   { get; set; }
    public string Nume { get; set; }

    public bool Equals(Produs other)
        => other != null && this.Id == other.Id;

Genericele sunt pilonul pe care se sprijină întreaga bibliotecă modernă .NET. LINQ, colecțiile, task-urile asincrone (Task<T>), injectarea de dependențe, și zeci de pattern-uri de design comune în C# — toate folosesc generice ca fundament. Static vs Dinamic — comparație

Polimorfismul static și cel dinamic nu sunt în competiție — se completează. Înțelegerea diferențelor te ajută să alegi instrumentul potrivit pentru fiecare situație.

POLIMORFISM STATIC
  • Rezolvat la momentul compilării
  • Bazat pe supraîncărcare și generice
  • Performanță maximă — fără overhead
  • Siguranță completă la compilare
  • Nu necesită virtual / override
  • Tipul obiectului nu contează la runtime
  • Ideal pentru operații pe tipuri diferite de date
  • Util în algoritmi și structuri de date generice
POLIMORFISM DINAMIC
  • Rezolvat la momentul execuției
  • Bazat pe moștenire și metode virtuale
  • Mic overhead din vtable lookup
  • Flexibilitate — noi tipuri fără recompilare
  • Necesită virtual, override, abstract
  • Tipul real al obiectului decide metoda
  • Ideal pentru ierarhii de obiecte cu comportament diferit
  • Util în design patterns și sisteme extensibile

1 Exemplu comparativ complet

Comparatie.csC#
// ─── STATIC: supraîncărcare ───────────────────────────────
public class AfisatorStatic
{
    public void Afiseaza(int val)
        => Console.WriteLine($"Int: {val}");

    public void Afiseaza(string val)
        => Console.WriteLine($"String: {val}");
}
// Compilatorul decide imediat. Fără surprize la runtime.


// ─── DINAMIC: metode virtuale ─────────────────────────────
public abstract class Animal
{
    public abstract void Sunet();  // obligatoriu de implementat
}

public class Caine : Animal
{
    public override void Sunet()
        => Console.WriteLine("Ham!");
}

public class Pisica : Animal
{
    public override void Sunet()
        => Console.WriteLine("Miau!");
}

// La runtime, C# vede că obiectul este Caine și apelează Ham!
Animal a = new Caine();
a.Sunet(); // → Ham!  (decizie la RUNTIME)

2 Exemplu practic combinat — amândouă în același proiect

În realitate, cele două forme coexistă în același cod. Iată un exemplu de sistem de rapoarte care folosește ambele tipuri de polimorfism în mod complementar.

SistemRapoarte.cs — combinatC#
// ── Polimorfism DINAMIC: ierarhie de tipuri de raport ─────
public abstract class Raport
{
    public string Titlu { get; set; }
    public abstract string Genereaza();  // fiecare tip știe cum se generează
}

public class RaportPDF : Raport
{
    public override string Genereaza() => $"[PDF] {Titlu}.pdf";
}

public class RaportExcel : Raport
{
    public override string Genereaza() => $"[XLS] {Titlu}.xlsx";
}

public class RaportHTML : Raport
{
    public override string Genereaza() => $"[HTML] {Titlu}.html";
}


// ── Polimorfism STATIC: supraîncărcare pentru salvare ─────
public class Manager
{
    // Supraîncărcare — salvare locală
    public void Salveaza(Raport r, string cale)
        => Console.WriteLine($"Salvez {r.Genereaza()} în {cale}");

    // Supraîncărcare — salvare cu backup
    public void Salveaza(Raport r, string cale, bool backup)
    {
        if (backup) Console.WriteLine("Creez backup...");
        Salveaza(r, cale);
    }

    // Supraîncărcare generică — salvare în colecție
    public void SalveazaTot<T>(IEnumerable<T> rapoarte, string cale)
        where T : Raport
    {
        foreach (var r in rapoarte)
            Salveaza(r, cale);
    }
}

// Utilizare — amândouă polimorfismele în acțiune
Manager mgr = new Manager();
List<Raport> lista = new List<Raport>
{
    new RaportPDF   { Titlu = "Vânzări"   },
    new RaportExcel { Titlu = "Inventar"  },
    new RaportHTML  { Titlu = "Dashboard" }
};

mgr.SalveazaTot(lista, "/output");
// → [PDF] Vânzări.pdf     (dinamic: știe că e RaportPDF)
// → [XLS] Inventar.xlsx   (dinamic: știe că e RaportExcel)
// → [HTML] Dashboard.html  (dinamic: știe că e RaportHTML)
🔍 ANALIZĂ

În exemplul de mai sus, SalveazaTot<T> este polimorfism static — compilatorul știe la build time că T este Raport sau o subclasă a sa. Dar r.Genereaza() în interiorul acelei metode este polimorfism dinamic — la runtime C# determină dacă r este RaportPDF, RaportExcel sau altceva și apelează metoda suprascrisă corespunzătoare.

Cele două mecanisme colaborează: genericele asigură că tipul este corect la compilare, iar metodele virtuale asigură comportamentul corect la runtime.

3 Când să folosești fiecare

✅ FOLOSEȘTE POLIMORFISM STATIC când...

Ai aceeași operație conceptuală dar cu tipuri de date diferite (ex: calcule numerice, conversii, formatări). Prioritatea este performanța — sisteme embedded, bucle critice, procesare de date în volum mare. Vrei că compilatorul să prindă orice greșeală de tip înainte de rulare. Lucrezi cu structuri de date generice (colecții, depozite, utilitare). Implentezi algoritmi matematici sau operații pe structuri de date imutabile.

✅ FOLOSEȘTE POLIMORFISM DINAMIC când...

Ai o familie de tipuri cu comportament diferit (animale, forme geometrice, angajați, tipuri de documente). Vrei să adaugi tipuri noi fără să modifici codul existent (principiul Open/Closed). Lucrezi cu liste de obiecte de tipuri diferite dar înrudite. Implementezi design patterns (Strategy, Observer, Factory, Command). Construiești sisteme care trebuie să fie extensibile de terți sau plugin-uri.

// ❌ GREȘEALĂ 3: new în loc de override — ascundere, nu polimorfism dinamic
public class Baza
{
    public virtual void Metoda() => Console.WriteLine("Baza");
}
public class Derivata : Baza
{
    public new void Metoda() => Console.WriteLine("Derivata"); // new!
}
Baza b = new Derivata();
b.Metoda(); // → "Baza"  ← SURPRIZĂ! new nu creează polimorfism dinamic

// ✅ CORECT: override pentru polimorfism dinamic real
public class DerivataBuna : Baza
{
    public override void Metoda() => Console.WriteLine("DerivataBuna");
}
Baza b2 = new DerivataBuna();
b2.Metoda(); // → "DerivataBuna"  ← polimorfism dinamic corect
⚠️ CUVÂNTUL CHEIE new — MAI RAU DECÂT PARE

Folosirea cuvântului cheie new pentru a "ascunde" o metodă din clasa bază (method hiding) este una dintre cele mai frecvente surse de confuzie în C#. Compilatorul nu va da eroare, dar comportamentul la runtime va fi surprinzător: dacă referința este de tipul clasei baze, se apelează metoda din bază, nu din derivată — indiferent de tipul real al obiectului. Evită new pentru metode decât dacă știi exact ce faci și de ce.
